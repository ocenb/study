# Виртуальные и платформенные потоки в Java 21

В эксперименте сравнивались три способа выполнить одинаковые задачи с имитацией ожидания ввода-вывода. На 10 000 задачах медианное время составило 179 мс при прямом запуске виртуальных потоков, 216 мс при использовании `StructuredTaskScope` и 1 536 мс при запуске платформенных потоков. В каждом режиме завершились все 10 000 задач.

## 1. Задача и способы запуска

В [VirtualThreadsDemo.java](VirtualThreadsDemo.java) каждая задача печатает имя из `Thread.currentThread().getName()`, ждёт заданное время через `Thread.sleep()` и увеличивает общий счётчик завершений. По умолчанию создаётся 10 000 задач с задержкой 100 мс. `sleep()` имитирует задержку ответа внешнего сервиса. При таком ожидании JVM может снять виртуальный поток с потока-носителя, чтобы тот выполнял другие задачи. Платформенный поток связан с собственным потоком ОС на протяжении всего своего жизненного цикла. [Документация Oracle о виртуальных потоках](https://docs.oracle.com/en/java/javase/21/core/virtual-threads.html)

| Режим | Создание потоков | Ожидание завершения |
| --- | --- | --- |
| `virtual` | `Thread.ofVirtual().name("virtual-", 0).start(...)` | `Thread.join()` для каждого запущенного потока |
| `platform` | `new Thread(...)` и `start()` | `Thread.join()` для каждого запущенного потока |
| `scope` | `scope.fork(...)` с фабрикой именованных виртуальных потоков | `scope.join().throwIfFailed()` и закрытие области |

Каждой задаче соответствует отдельный поток. В двух прямых режимах программа сначала запускает потоки, затем ожидает их завершения. При сбое запуска или прерывании ожидания она прерывает уже запущенные потоки и дожидается их выхода. После штатного запуска программа сверяет счётчик завершений с числом задач.

В трёх запусках с включённым выводом проверено по 10 000 уникальных имён и по 10 000 завершений. Порядок вывода зависит от планирования потоков. В этом фрагменте видны первые три имени и итоговая строка виртуального режима.

```text
virtual-1
virtual-4
virtual-5
…
mode=virtual tasks=10000 completed=10000 sleep_ms=100 wall_ms=585.926 cpu_ms=1062.500
```

## 2. Обработка исключений и отмена в StructuredTaskScope

Владелец создаёт `StructuredTaskScope.ShutdownOnFailure` в `try-with-resources` и регистрирует каждую подзадачу через `fork()`. При штатном завершении `join()` дожидается всех подзадач. При первой ошибке область прерывает незавершённые потоки, `join()` возвращает управление, а `throwIfFailed()` передаёт владельцу `ExecutionException` с исходной причиной. Выход из `try-with-resources` закрывает область и дожидается остановки её потоков. Подзадачи должны реагировать на прерывание. [Документация Java 21 по ShutdownOnFailure](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/StructuredTaskScope.ShutdownOnFailure.html)

В режиме `cancel` одна подзадача готовится к 30-секундному ожиданию и сигнализирует о готовности через `CountDownLatch`. Вторая после сигнала выбрасывает `IllegalStateException`. Первая получает `InterruptedException`. После закрытия области программа проверяет и факт прерывания, и причину `ExecutionException`. Обе строки появились в каждом из пяти проверочных запусков.

```text
scope-0 interrupted
scope failure: java.lang.IllegalStateException: simulated I/O failure
```

## 3. Замеры времени и ресурсов

Измерения выполнены 8 ноября 2026 года на Windows x64, сборка 26200, с Amazon Corretto 21.0.13 и процессором Intel Core i3-1115G4. JVM видела 4 логических процессора. Для каждого сочетания режима и размера нагрузки запускалась новая JVM, всего по три повтора. Порядок режимов сдвигался между повторами. Задержка составляла 100 мс, вывод имён был отключён через `--quiet`, чтобы скорость записи в консоль не влияла на сравнение.

- **Время выполнения** измерено через `System.nanoTime()` от начала запуска задач до завершения ожидания. Запуск JVM и печать итоговой строки находятся за пределами этого интервала.
- **Время CPU** получено как разность показаний `OperatingSystemMXBean.getProcessCpuTime()` за тот же участок. Это суммарное процессорное время JVM, включая её служебные потоки. При работе на нескольких ядрах оно может превышать прошедшее время.
- **Память** измерена скриптом [benchmark.ps1](benchmark.ps1). Скрипт примерно каждые 20 мс считывает накопленный пик рабочего набора JVM (`PeakWorkingSet64`) и сохраняет наибольшее показание. Это оценка пика резидентной памяти всего процесса, включая базовое потребление JVM.

В таблице приведены медианы трёх показаний для каждого столбца. Все 27 запусков завершили заданное число задач.

При 100 задачах диапазоны времени выполнения пересекались. На 10 000 задачах три запуска `virtual` заняли 174–271 мс, а три запуска `platform` заняли 1 424–1 631 мс. Медианное время виртуального режима было в 8,6 раза меньше, суммарное время CPU — в 8,2 раза меньше, а пиковый рабочий набор — в 4,4 раза меньше. Эти отношения относятся к данной машине и нагрузке с ожиданием. На коротких прогонах на результаты влияют прогрев JVM, точность системных счётчиков и фоновая нагрузка.

## 4. Воспроизведение

Нужен JDK 21 в `PATH`. В этой версии `StructuredTaskScope` является предварительным API, поэтому флаг `--enable-preview` нужен и при компиляции, и при запуске. Команды выполняются в PowerShell на Windows из корня репозитория.

```powershell
Set-Location .\multithreading\virtual-threads
$classes = Join-Path $env:TEMP ('virtual-threads-' + [guid]::NewGuid())
New-Item -Path $classes -ItemType Directory | Out-Null
javac --release 21 --enable-preview -d $classes .\VirtualThreadsDemo.java

java --enable-preview -cp $classes VirtualThreadsDemo virtual 10000 100
java --enable-preview -cp $classes VirtualThreadsDemo platform 10000 100
java --enable-preview -cp $classes VirtualThreadsDemo scope 10000 100
java --enable-preview -cp $classes VirtualThreadsDemo cancel

.\benchmark.ps1 -Classes $classes | Format-Table -AutoSize
```

## 5. Выводы

Виртуальные потоки оказались выгодны при большом числе задач, проводящих большую часть времени в ожидании. Потоки-носители могут обслуживать другие задачи, пока виртуальные потоки спят. При большом числе платформенных потоков растут затраты на их создание и обслуживание. Для вычислительной нагрузки предел параллелизма по-прежнему задаётся доступными ядрами CPU.

`StructuredTaskScope` даёт тому же набору виртуальных потоков общий жизненный цикл. Владелец ждёт результаты, получает причину сбоя и при ошибке одной подзадачи может дождаться остановки остальных после их автоматического прерывания. Такая схема подходит для запроса, результат которого зависит от нескольких параллельных обращений к внешним сервисам.
