# Отчёт о выполнении практического задания: Состояния потоков в Java

## 1. Цель работы
Изучить и продемонстрировать на практике все 6 жизненных состояний потока в Java (`java.lang.Thread.State`):
1. **NEW** — поток создан, но ещё не запущен (до вызова `.start()`).
2. **RUNNABLE** — поток выполняется в JVM (активно вычисляет или готов к вычислениям в ОС).
3. **BLOCKED** — поток заблокирован в ожидании монитора блокировки `synchronized`.
4. **WAITING** — поток бессрочно ожидает действия от другого потока (`Object.wait()`, `Thread.join()` без таймаута).
5. **TIMED_WAITING** — поток ожидает действия от другого потока с указанием максимального времени ожидания (`Thread.sleep()`, `Object.wait(timeout)`).
6. **TERMINATED** — поток завершил выполнение своего метода `run()`.

---

## 2. Архитектура решения

В проекте созданы следующие компоненты:
1. **`com.example.demo.states.ThreadStateDemoService`**:
   - Сервисный класс, организующий скоординированный запуск 3 исследуемых потоков и потока-наблюдателя (`ThreadStateObserver`).
2. **`com.example.demo.states.StateTransitionEvent`**:
   - Модель события смены/фиксации состояния потока (`timestamp`, `threadName`, `state`, `description`).
3. **`com.example.demo.states.ThreadStateController`**:
   - REST API для удаленного вызова демонстрации (`POST /api/thread-states/run`) и получения истории переходов (`GET /api/thread-states/history`).
4. **`com.example.demo.ThreadStateDemoTest`**:
   - Комплексные интеграционные тесты, проверяющие фиксацию каждого из 6 состояний и доступность REST эндпоинтов.

---

## 3. Описание исследуемых потоков и их состояний

Для демонстрации используются 3 независимых потока, каждый из которых проходит через уникальную последовательность состояний:

| Имя потока | Проходимые состояния | Механизм перехода |
| :--- | :--- | :--- |
| **`TimedWaitingWorker`** | `NEW` → `RUNNABLE` → `TIMED_WAITING` → `RUNNABLE` → `TERMINATED` | Вызов `Thread.sleep(600)` |
| **`WaitingWorker`** | `NEW` → `RUNNABLE` → `WAITING` → `RUNNABLE` → `TERMINATED` | Вызов `waitLock.wait()` и последующий `waitLock.notifyAll()` |
| **`BlockedWorker`** | `NEW` → `RUNNABLE` → `BLOCKED` → `RUNNABLE` → `TERMINATED` | Попытка захвата монитора `synchronized (blockLock)`, удерживаемого главным потоком |

---

## 4. Этапы выполнения задания

### Этап 1. Создание потоков (состояние NEW)
* Создаются 3 экземпляра потоков `timedWaitingWorker`, `waitingWorker`, `blockedWorker`.
* До вызова метода `.start()` опрашивается состояние `getState()`, подтверждая состояние **`NEW`**.

### Этап 2. Запуск и переход в специфические состояния
* Главный поток предварительно захватывает монитор `blockLock` через `synchronized (blockLock)`.
* Запускаются все 3 потока:
  1. `timedWaitingWorker` переходит в **`RUNNABLE`**, выполняет полезную работу и уходит в сон через `Thread.sleep(600)`, принимая состояние **`TIMED_WAITING`**.
  2. `waitingWorker` переходит в **`RUNNABLE`**, захватывает `waitLock` и вызывает `waitLock.wait()`, переходя в состояние бессрочного ожидания **`WAITING`**.
  3. `blockedWorker` переходит в **`RUNNABLE`** и пытается войти в блок `synchronized (blockLock)`, но поскольку монитор занят главным потоком, переходит в состояние **`BLOCKED`**.

### Этап 3. Реализация механизма наблюдения (Observer)
* Создан фоновый поток-демон `ThreadStateObserver`, непрерывно с интервалом в 10 мс отслеживающий метод `getState()` каждого исследуемого потока.
* При любом изменении состояния наблюдатель фиксирует событие в журнал и мгновенно выводит уведомление в консоль:  
  `>>> [НАБЛЮДАТЕЛЬ] Поток '<Name>': <OLD_STATE> -> <NEW_STATE>`
* Сервис также выводит наглядные таблицы снимков состояний потоков на каждом этапе (фазы 1, 2, 3).

### Этап 4. Освобождение ресурсов и завершение (состояние TERMINATED)
* Главный поток выходит из синхронизированного блока `blockLock`, освобождая монитор. Поток `blockedWorker` захватывает его, отрабатывает и завершается.
* Главный поток отправляет сигнал `waitLock.notifyAll()`, пробуждая `waitingWorker`.
* Поток `timedWaitingWorker` просыпается по истечении таймаута сна.
* Главный поток ожидает окончания работы всех потоков через метод `.join()`.
* После завершения опрашивается `getState()`, подтверждая состояние **`TERMINATED`** для всех трёх потоков.

### Этап 5. Тестирование
* Написаны автоматические тесты `ThreadStateDemoTest`:
  - Проверено присутствие всех 6 состояний в журнале событий (`NEW`, `RUNNABLE`, `BLOCKED`, `WAITING`, `TIMED_WAITING`, `TERMINATED`).
  - Проверена корректность работы REST эндпоинтов через `MockMvc`.
  - Все тесты пройдены успешно (10/10 тестов проекта).
