# Отчёт о выполнении практического задания: Сравнение производительности `stream()` и `parallelStream()`

## 1. Введение и цель работы
Цель работы — практическое исследование производительности последовательной (`stream()`) и параллельной (`parallelStream()`) обработки коллекций в Java на примере массива из **1 000 000 случайных чисел**.

В соответствии с заданием над элементами выполняются следующие типовые операции поточной обработки:
1. **Фильтрация (`filter`)**: отбор только чётных чисел (`n % 2 == 0`).
2. **Преобразование (`map`)**: умножение отобранных значений на 2 (`n * 2`).
3. **Агрегация (`reduce` / `sum`)**: вычисление итоговой суммы всех преобразованных элементов.

Аппаратная платформа тестирования:
- **Процессор**: 12 логических ядер (доступно `Runtime.getRuntime().availableProcessors() == 12`).
- **JVM**: OpenJDK 21.0.2 LTS.

## 2. Описание каждого этапа выполнения задания

### Этап 1. Архитектура и подготовка данных
* В пакете `com.example.demo.stream` создан класс [`StreamBenchmarkService`](file:///d:/projects/study/multithreading/demo/src/main/java/com/example/demo/stream/StreamBenchmarkService.java).
* Метод `generateRandomList(1_000_000)` генерирует список `ArrayList<Integer>` размером в 1 000 000 псевдослучайных чисел с фиксированным seed для повторяемости замеров.
* Создан DTO [`BenchmarkResultDto`](file:///d:/projects/study/multithreading/demo/src/main/java/com/example/demo/stream/BenchmarkResultDto.java) для сохранения метрик: времени в наносекундах и миллисекундах, коэффициента ускорения (`speedupFactor`), итоговой суммы и флага совпадения результатов.

### Этап 2. Реализация конвейера обработки данных
Реализованы два сценария вычислений:
1. **Базовый сценарий (легкие операции)**:
   ```java
   numbers.stream()
          .filter(n -> n % 2 == 0)
          .mapToLong(n -> (long) n * 2)
          .sum();
   ```
   и его параллельный эквивалент:
   ```java
   numbers.parallelStream()
          .filter(n -> n % 2 == 0)
          .mapToLong(n -> (long) n * 2)
          .sum();
   ```
2. **Тяжелый сценарий (вычислительно-интенсивные операции)**:
   В операцию преобразования добавлен цикл тригонометрических расчётов, что позволяет наглядно исследовать модель $N \times Q$ (где $Q$ — вычислительная сложность обработки одного элемента).

### Этап 3. Методология измерений и JIT Warm-up
* Замеры времени производились с помощью `System.nanoTime()` с точностью до наносекунд.
* Перед основными замерами реализована фаза прогрева JVM (`warmUpJvm`), в ходе которой оба конвейера прогоняются 3 раза. Это позволяет JIT-компилятору (C2) скомпилировать и оптимизировать байткод, исключая накладные расходы компиляции из результатов замеров.
* Каждое измерение повторяется в серии итераций (3–5 прогонов), после чего вычисляется устойчивое среднее значение.
* На каждом шаге контролируется строгое совпадение сумм: `seqSum == parSum`.

### Этап 4. Разработка REST API и интеграционное тестирование
* Создан контроллер [`StreamBenchmarkController`](file:///d:/projects/study/multithreading/demo/src/main/java/com/example/demo/stream/StreamBenchmarkController.java) с эндпоинтом `POST /api/streams/benchmark`.
* Написаны автоматические тесты [`StreamBenchmarkTest`](file:///d:/projects/study/multithreading/demo/src/test/java/com/example/demo/StreamBenchmarkTest.java), проверяющие идентичность результатов вычислений и корректность REST API.

## 4. Объяснение причин различий в производительности

1. **Разделение данных (Splitting Overhead)**:
   * `parallelStream()` использует `Spliterator` для деления коллекции на поддиапазоны по алгоритму *Fork/Join* (`ForkJoinPool.commonPool()`).
   * Для `ArrayList` деление происходит эффективно ($O(1)$ по индексам), однако создание подзадач и координация потоков всё равно требуют затрат тактов CPU.
2. **Стоимость операции на один элемент (NQ-модель)**:
   * Эмпирическое правило Java Streams гласит: параллелизм выгоден, когда $N \times Q > 10\,000$, где:
     * $N$ — число элементов (в нашем случае $1\,000\,000$);
     * $Q$ — процессорные затраты на обработку одного элемента.
   * При $Q$ тривиальном (просто `n * 2`) затраты на элемент ничтожны. Ускорение составило **3.89x** (вместо теоретических 12x), поскольку узким местом стала пропускная способность шины памяти и распаковка объектов (`Integer` $\rightarrow$ `long`).
   * При высоком $Q$ (сложные вычисления `heavyCalculation`) время работы CPU на ядрах многократно превышает накладные расходы координации. Ускорение достигло **8.93x** (почти линейно относительно доступных ядер).
3. **Боксинг и кэш-память (Memory Bandwidth & Cache Locality)**:
   * Коллекция `List<Integer>` хранит ссылки на объекты `Integer`, разбросанные в куче (heap). Это приводит к частым промахам кэша L1/L2/L3 (cache misses) при параллельном обходе несколькими ядрами. Примитивные массивы (`int[]` или `IntStream`) показывают еще более высокую параллельную масштабируемость.
4. **Слияние результатов (Reduction Overhead)**:
   * В конце параллельного конвейера частные суммы подпотоков суммируются в единое число через `ForkJoinTask.join()`. Для ассоциативных операций вроде суммы эта фаза крайне быстра.

## 5. Итоговые выводы: когда использовать `stream()`, а когда `parallelStream()`

### Когда предпочтителен `parallelStream()`:
1. **Большой объём данных ($N \ge 10\,000$–$100\,000$)** в сочетании с ресурсоёмкими вычислениями на каждый элемент (высокий $Q$).
2. **Структуры данных с дешевым делением**: массивы `int[]`, `long[]`, `ArrayList`, диапазоны `IntStream.range()`. Они делятся на равные части за $O(1)$.
3. **Вычислительные задачи (CPU-bound)**, не блокирующие потоки операциями ввода-вывода (I/O).
4. **Операции без состояния (stateless)** и ассоциативные функции редукции, не требующие синхронизации между потоками.

### Когда предпочтителен `stream()`:
1. **Малые и средние объёмы данных ($N < 10\,000$)**: накладные расходы на создание потоков и разделение задач превышают выигрыш от параллелизма.
2. **Плохо разделяемые структуры данных**: `LinkedList`, `Stream.iterate`, каналы I/O. Разделение связного списка требует последовательного обхода элементов ($O(N)$), сводя выгоду к нулю.
3. **Операции, зависящие от порядка (`findFirst`, `limit`, `skip`)**: параллельные стримы тратят много ресурсов на поддержание строгого порядка появления элементов (`encounter order`).
4. **Высоконагруженные серверные окружения (Web / Spring Boot)**:
   * `parallelStream()` по умолчанию использует общий пул JVM `ForkJoinPool.commonPool()`.
   * Если сервер одновременно обрабатывает сотни HTTP-запросов, запуск параллельных стримов внутри запросов может исчерпать общий пул потоков и заблокировать обработку других пользователей.

## 6. Примечания о влиянии параллелизма на производительность

1. **Закон Амдала ($S = \frac{1}{(1 - P) + \frac{P}{N}}$)**:
   * Даже если 90% алгоритма распараллелено ($P = 0.9$), оставшиеся 10% последовательного кода (создание стрима, итоговое слияние) фундаментально ограничивают максимальное теоретическое ускорение независимо от числа доступных ядер CPU.
2. **Конкуренция за общие ресурсы (False Sharing & Memory Bus Contention)**:
   * При высокой плотности параллельных потоков узким местом становится не тактовая частота ядер, а пропускная способность общей шины памяти DDR и синхронизация кэш-линий между ядрами.
3. **Влияние на сборщик мусора (GC Pressure)**:
   * Параллельные потоки генерируют временные объекты и кадры задач параллельно во всех ядрах, что увеличивает скорость заполнения поколения `Eden` и приводит к более частым паузам сборки мусора (GC), если конвейер использует боксинг (`Integer`, `Double`).
