# Отчёт: volatile, AtomicInteger и singleton-кэш на AtomicReference

## Цель и состав решения

Реализованы безопасная остановка работающих потоков, общий атомарный счётчик и ленивый singleton-кэш. Решение находится в `src/main/java/com/example/demo/atomics` и запускается отдельно от Spring Boot, без HTTP и базы данных.

| Файл | Назначение |
| --- | --- |
| `StopSignal.java` | Одноразовый флаг остановки `volatile boolean` |
| `AtomicCounter.java` | Инкремент и чтение через `AtomicInteger` |
| `SingletonCache.java` | Единственный экземпляр кэша и публикация строки через `AtomicReference` |
| `AtomicsDemo.java` | Совместная нагрузка, остановка, сравнение с `synchronized` |
| `src/test/java/com/example/demo/atomics/AtomicsTest.java` | Проверки корректности и пример потери обновлений |
| `ATOMICS_RESULTS.txt` | Полный фактический вывод нагрузочного запуска |

## 1. Остановка через volatile

В `StopSignal` поле `stopped` первоначально равно `false`. Метод `stop()` записывает `true`, а `isStopped()` читает флаг в условии рабочего цикла:

```java
while (!stop.isStopped() && completed < iterations) {
    counter.increment();
    String cached = cache.getOrCreate();
    // Проверка идентичности ссылки и локальный учёт операций.
    completed++;
}
```

Запись и последующее чтение `volatile` обеспечивают межпоточную видимость и отношение happens-before. Это позволяет потоку заметить запрос остановки; `volatile` не гарантирует конкретного времени планирования потока. Остановка кооперативная: уже начатая итерация может завершиться после записи флага. Поэтому итоговый счётчик читается после ожидания всех задач, а не сразу после `stop()`.

Сигнал одноразовый: повторный запуск создаёт новый `StopSignal`. Нагрузочный цикл не выполняет блокирующий ввод-вывод. Если бы поток ожидал ввод или находился в длительном `sleep()`, одной записи флага было бы недостаточно для немедленного пробуждения — понадобился бы соответствующий механизм отмены, например `interrupt()`.

Проверка `volatileFlagStopsRunningThread` запускает поток, дожидается его старта, устанавливает флаг и проверяет завершение с ограниченным ожиданием. Нагрузочный сценарий дополнительно выполняет инкременты и обращения к кэшу до остановки.

## 2. Счётчик через AtomicInteger

`AtomicCounter` содержит `AtomicInteger`, изначально равный нулю:

```java
public int increment() {
    return value.incrementAndGet();
}

public int get() {
    return value.get();
}
```

`incrementAndGet()` выполняет увеличение как единую атомарную операцию. Параллельные инкременты не теряются. Возвращённое значение относится к моменту конкретного инкремента: другой поток может сразу увеличить счётчик дальше.

Отдельный тест выполняет 100 000 инкрементов в каждом из восьми потоков и требует ровно **800 000** после их завершения. Совместная нагрузка проверяет итог для 1, 2, 4 и 8 потоков. Число итераций ограничивается так, чтобы ожидаемый результат фиксированной нагрузки помещался в `int`; сам `AtomicInteger` от переполнения не защищает.

## 3. Singleton-кэш через AtomicReference

`SingletonCache` имеет закрытый конструктор и единственный `static final INSTANCE`. Инициализация класса обеспечивает безопасное создание самого singleton в пределах одного загрузчика классов. Содержимое кэша создаётся лениво и хранится в `AtomicReference<String>`.

Алгоритм `getOrCreate()`:

1. Прочитать текущее значение. Если оно существует, вернуть его.
2. Создать строку-кандидат.
3. Вызвать `compareAndSet(null, candidate)`.
4. Победитель возвращает свой кандидат; проигравшие читают и возвращают сохранённую строку победителя.

Сброс и замена значения не предусмотрены, поэтому чтение после неуспешного CAS возвращает ненулевой объект. Строка неизменяема, что упрощает безопасное совместное использование. Атомарность ссылки сама по себе не защищала бы последующие изменения полей изменяемого объекта.

При гонке могут создаться несколько временных кандидатов. Гарантия состоит в единственном опубликованном значении и одной возвращаемой ссылке, а не в единственном вызове конструктора. Поэтому создание кандидата не должно выполнять платежи, запись в файл или другие действия, которые нельзя повторять. В примере используется `new String(...)`, чтобы сравнение ссылок не маскировалось интернированием строковых литералов.

Тест сравнивает объекты через `assertSame`, а не только содержимое через `equals`. Каждый из восьми потоков многократно получает ту же ссылку.

## 4. Нагрузочное тестирование

Каждая рабочая итерация читает volatile-флаг, увеличивает общий счётчик, обращается к общему кэшу и проверяет ссылку. Потоки ожидают общего сигнала старта; создание пула и ожидание готовности находятся за пределами измеряемого участка. Время замеряется через `System.nanoTime()` от разрешения старта до получения результатов всех задач. Печать выполняется после измерения.

Для сравнения используется корректный счётчик с `synchronized increment()` и `synchronized get()`. В обоих вариантах одинаковы флаг, кэш и объём работы. Это сравнение стоимости атомарного инкремента и монитора внутри общего сценария; оно не изолирует стоимость каждой volatile-операции или каждого чтения `AtomicReference`.

Для каждого количества потоков проведены три прогревочных запуска каждого варианта, затем пять измерений. Порядок вариантов чередуется. В таблице указана медиана, диапазон и пропускная способность по медиане. На один поток приходится 250 000 итераций. Проверка результата выполняется после каждого запуска; ошибка приводит к исключению. Ожидания ограничены таймаутами, а пул завершается в `finally`.

## 5. Корректные и некорректные ситуации

| Ситуация | Оценка и объяснение |
| --- | --- |
| `volatile boolean stop` в рабочем цикле | Корректно для видимости однонаправленного запроса остановки |
| Обычный `boolean stop` без синхронизации | Гонка данных: рабочий поток не обязан заметить изменение; зависание не обязано воспроизводиться каждый раз |
| `volatile int count; count++` | Некорректно: чтение, сложение и запись не становятся одной атомарной операцией |
| `AtomicInteger.incrementAndGet()` | Корректный инкремент без потери обновлений |
| `counter.set(counter.get() + 1)` | Некорректно: два атомарных вызова вместе не образуют атомарный инкремент |
| `if (reference.get() == null) reference.set(candidate)` | Некорректная инициализация: несколько потоков могут заменить значение и вернуть разные объекты |
| `compareAndSet(null, candidate)` с возвратом победителя | Корректно для однократной публикации кэша |
| Возврат своего кандидата после проигрыша CAS | Некорректно: вызывающий получает объект, которого нет в кэше |
| Изменение полей объекта внутри `AtomicReference` | Требует отдельного решения для синхронизации полей или неизменяемых снимков |

В тесте `volatileReadThenWriteCanLoseUpdates` потеря обновлений демонстрируется воспроизводимо. Два потока 100 раз читают одинаковое значение, ждут друг друга на барьере, затем оба записывают `previous + 1`. После 200 логических инкрементов получается **100**. Барьеры намеренно задают допустимое чередование составной операции `++`; они не используются в сравнительном бенчмарке. Тест не зависит от случайного воспроизведения гонки.

## 6. Запуск и проверка

Из каталога `multithreading/demo`, с установленным JDK 17 или новее:

```sh
# Компиляция и консольный запуск без Maven и Spring.
mkdir -p target/atomics-demo
javac -encoding UTF-8 -d target/atomics-demo src/main/java/com/example/demo/atomics/*.java
java -cp target/atomics-demo com.example.demo.atomics.AtomicsDemo

# Только проверки задания.
sh ./mvnw -Dtest=com.example.demo.atomics.AtomicsTest test

# Все тесты проекта.
sh ./mvnw test
```

Для сохранения нового вывода можно добавить `> ATOMICS_RESULTS.txt` к команде запуска. Числа могут отличаться от приведённых, но равенство счётчика числу операций и идентичность ссылок должны сохраняться.

## 7. Выводы

`volatile` подходит для видимости флага и кооперативной остановки, но не делает составные действия атомарными. `AtomicInteger` решает задачу конкурентного увеличения одного счётчика. `AtomicReference` позволяет атомарно опубликовать единственное значение кэша; неизменяемость строки обеспечивает безопасное дальнейшее чтение.

Эти средства обеспечивают корректность конкретных операций, а не произвольной последовательности действий. Для инвариантов над несколькими полями может понадобиться блокировка или другой алгоритм. Производительность следует оценивать при реальной конкуренции: общий атомарный счётчик тоже способен стать ограничением масштабирования.
