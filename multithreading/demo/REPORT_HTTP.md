# Краткий отчёт: асинхронные HTTP-запросы через ThreadPoolExecutor

## 1. Приём списка URL

Приложение `AsyncHttpApplication` принимает URL аргументами командной строки или из UTF-8 файла через `--file`. В файле каждый URL занимает отдельную строку; пустые строки и комментарии с `#` пропускаются. Повторяющиеся адреса сохраняются как отдельные запросы.

В `urls-http.txt` подготовлены **20 публичных URL** JSONPlaceholder: по пять адресов ресурсов `posts`, `todos`, `users`, `comments`. API-ключ не требуется. Поддерживаются абсолютные HTTP/HTTPS URL; некорректный адрес попадает в результаты как ошибка, не отменяя остальные запросы.

Исходники находятся в `src/main/java/com/example/demo/http/`:

- `AsyncHttpApplication.java` — чтение входных данных и вывод сводки.
- `AsyncHttpService.java` — настройка пула, асинхронный HTTP, сбор результатов и закрытие ресурсов.

## 2. Настройка пула и отправка запросов

`ThreadPoolExecutor` создаётся вручную, без `Executors.newFixedThreadPool()` в приложении:

| Параметр | Значение |
| --- | --- |
| Основное число потоков | 4 |
| Максимальное число потоков | 8 |
| Очередь | `ArrayBlockingQueue`, ёмкость 64 |
| Время простоя дополнительных потоков | 30 секунд |
| Имена потоков | `async-http-worker-N` |
| Политика насыщения | `CallerRunsPolicy` |

Пул передаётся в `HttpClient.newBuilder().executor(executor)`. Для каждого адреса вызывается **`sendAsync()`**; все запросы запускаются до общего ожидания через `CompletableFuture.allOf()`. Потоки приложения не блокируются на отдельном `send()`.

При заполнении очереди пул может вырасти до восьми потоков; при полном насыщении `CallerRunsPolicy` выполняет задачу в вызывающем потоке. Число потоков пула не равно числу одновременно открытых HTTP-соединений: транспорт асинхронный. В публичном запуске максимальный фактический размер пула составил четыре потока.

Настроены таймаут соединения **3 секунды** и таймаут запроса **5 секунд**. Дополнительный `CompletableFuture.orTimeout()` ограничивает ожидание всего ответа, включая тело. При истечении срока отменяется исходный HTTP future. Тело ответа отбрасывается через `BodyHandlers.discarding()`. При прерывании координатора незавершённые запросы отменяются; после работы пул закрывается через `shutdown()` с ограниченным ожиданием завершения.

## 3. Сбор результатов и сводка

Для каждого входного URL сохраняются HTTP-код либо причина ошибки и время через `System.nanoTime()`. Результаты выводятся в исходном порядке, независимо от порядка завершения запросов.

Ответы 2xx считаются успешными; прочие полученные HTTP-коды учитываются отдельно от сетевых ошибок, неверных URL и таймаутов. Отсутствующий HTTP-код выводится как `—`, а не как вымышленный код `0`.

Длительность измеряется от начала подготовки запроса до завершения чтения/отбрасывания ответа либо фиксации ошибки. Она включает клиентские накладные расходы, ожидание выполнения, соединение и передачу данных; это не только время обработки на сервере. Сводка содержит среднее, минимум, максимум по всем результатам, включая ошибки, и общее время партии.

## 4. Проверка и фактические результаты

Среда: Java 17.0.20.1, Linux. Проведены реальный запуск на публичных URL и воспроизводимый запуск на локальном HTTP-сервере.

| Запуск | URL | 2xx | HTTP не-2xx | Ошибки запросов | Время партии |
| --- | ---: | ---: | ---: | ---: | ---: |
| Публичный JSONPlaceholder | 20 | 20 | 0 | 0 | 1521,602 мс |
| Локальный сервер | 20 | 16 | 3 | 1 | 324,275 мс |

В публичном запуске все ответы имели код **200**; средняя длительность — **984,150 мс**, минимум — **855,347 мс**, максимум — **1501,162 мс**. Полный вывод: [HTTP_PUBLIC_RESULTS.txt](HTTP_PUBLIC_RESULTS.txt).

В локальном запуске получены четырнадцать ответов 200, два ответа 201, два ответа 404, один ответ 503 и один таймаут. Для него отдельно задан срок 300 мс. Сервер наблюдал до восьми одновременно активных обработчиков. Полный вывод: [HTTP_LOCAL_RESULTS.txt](HTTP_LOCAL_RESULTS.txt). После обоих запусков собственный пул сообщил `terminated=true`.

Семь новых тестов проверяют реальную параллельность четырёх запросов, порядок и повторение URL, HTTP-коды и статистику, сетевые ошибки и неверные адреса, таймаут заголовков и тела, отмену при прерывании, закрытие пула, файловый ввод и печать. Тест параллельности разрешает серверу ответить только после прихода всех четырёх запросов; он не опирается на сравнение нестабильных замеров времени.

Автоматические проверки прошли: **7 новых тестов, 0 ошибок и падений; полный набор проекта — 47 тестов, 0 ошибок и падений**. Для полного набора существующий Mockito подключался при старте тестовой JVM параметром `-DargLine=-javaagent:/tmp/study-maven/repository/org/mockito/mockito-core/5.17.0/mockito-core-5.17.0.jar`; конфигурация проекта не менялась.

Для сетевых проверок потребовался запуск вне sandbox, поскольку sandbox запрещает создание сокетов. Во временной Java для публичного HTTPS использовано хранилище системных корневых сертификатов; проверка TLS не отключалась. Приведённые задержки относятся к одному фактическому запуску и изменятся при повторении.

## Запуск

Из `multithreading/demo` с JDK 17 или новее:

```sh
mkdir -p target/http-demo
javac -encoding UTF-8 -d target/http-demo src/main/java/com/example/demo/http/*.java

# 20 публичных URL из файла.
java -cp target/http-demo com.example.demo.http.AsyncHttpApplication --file urls-http.txt

# Произвольные URL аргументами.
java -cp target/http-demo com.example.demo.http.AsyncHttpApplication https://example.com https://jsonplaceholder.typicode.com/posts/1

# Проверки задания и все тесты проекта.
sh ./mvnw -Dtest=com.example.demo.http.AsyncHttpServiceTest test
sh ./mvnw test
```

Для повторения локальной демонстрации без Maven:

```sh
javac -encoding UTF-8 -cp target/http-demo -d target/http-demo src/test/java/com/example/demo/http/LocalHttpFixture.java src/test/java/com/example/demo/http/LocalHttpDemo.java
java -cp target/http-demo com.example.demo.http.LocalHttpDemo
```

## Вывод

Приложение принимает список URL, отправляет асинхронные запросы с собственным вручную настроенным `ThreadPoolExecutor` и выводит HTTP-коды, длительности и сводку. Ошибки отдельных запросов не приводят к потере остальных результатов; таймауты и завершение пула ограничивают ожидание и освобождают ресурсы.
