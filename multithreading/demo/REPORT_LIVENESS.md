# Отчёт: Deadlock, Livelock и Starvation

## 1. Цель и состав решения

Цель — воспроизвести три проблемы прогресса потоков, диагностировать взаимную блокировку настоящим `jstack` и реализовать способы предотвращения.

| Файл | Назначение |
| --- | --- |
| `src/main/java/com/example/demo/liveness/DeadlockDemo.java` | Настоящий deadlock двух потоков в отдельной JVM |
| `src/main/java/com/example/demo/liveness/LivenessDemo.java` | Ограниченные демонстрации livelock и starvation, три исправления |
| `run-deadlock-diagnostics.sh` | Компиляция, запуск отдельной JVM, снятие `jstack`, завершение созданного процесса |
| `diagnostics/process.log` | Фактический вывод зависшей JVM с PID |
| `diagnostics/jstack.txt` | Полный исходный дамп потоков |
| `LIVENESS_RESULTS.txt` | Фактический вывод остальных сценариев |
| `src/test/java/com/example/demo/liveness/LivenessTest.java` | Автоматические проверки |

Среда выполнения: OpenJDK **17.0.20.1**, Linux, JVM видит **12 логических процессоров**. Примеры запускаются без Spring Boot и базы данных.

## 2. Создание Deadlock

Созданы два объекта-монитора: `resourceA` и `resourceB`.

- `Deadlock-1-A-then-B` захватывает A, затем пытается захватить B.
- `Deadlock-2-B-then-A` захватывает B, затем пытается захватить A.

Захват выполняется вложенными `synchronized`. `CountDownLatch(2)` гарантирует, что оба потока уже удерживают первые ресурсы, прежде чем начнут захватывать вторые. В отличие от `sleep()`, это задаёт воспроизводимое чередование. Ожидание latch внутри `synchronized(first)` **не освобождает монитор first**.

После достижения latch возникает цикл:

```text
Поток 1 удерживает A -> ждёт B -> B удерживает поток 2
Поток 2 удерживает B -> ждёт A -> A удерживает поток 1
```

Выполняются четыре условия взаимной блокировки: исключительное владение ресурсом, удержание одного ресурса при ожидании другого, отсутствие принудительного отъёма монитора и циклическое ожидание.

`ThreadMXBean.findMonitorDeadlockedThreads()` используется только для подтверждения готовности демонстрации. Затем основной поток вызывает `join()`. Рабочие потоки не являются daemon, поэтому JVM действительно остаётся зависшей. Это не имитация сообщения об ошибке и не ожидание с таймаутом вместо deadlock.

Фактический вывод процесса:

```text
PID=38217
Deadlock-2-B-then-A: первый ресурс захвачен
Deadlock-1-A-then-B: первый ресурс захвачен
DEADLOCK_CONFIRMED: оба потока BLOCKED. Снимите jstack <PID> или kill -3 <PID>.
```

Порядок первых двух сообщений и PID при повторном запуске могут отличаться.

## 3. Диагностика через jstack

Скрипт дождался подтверждения deadlock, выполнил следующую команду для созданного процесса и сохранил stdout инструмента в `diagnostics/jstack.txt`:

```sh
jstack -l 38217
```

Вокруг команды установлен внешний предел ожидания `timeout 15`. Первое подключение в sandbox оказалось недоступно; фактический приложенный дамп получен повторным запуском отдельной JVM и `jstack` вне sandbox. После успешного снятия дампа скрипт завершил только созданную им JVM. Никакие диагностические зависшие процессы оставлять работающими не требуется.

### Состояния потоков в настоящем дампе

Сокращённые фрагменты (полная версия сохранена отдельно):

```text
"Deadlock-1-A-then-B"
   java.lang.Thread.State: BLOCKED (on object monitor)
    at com.example.demo.liveness.DeadlockDemo.acquire(DeadlockDemo.java:27)
    - waiting to lock <0x000000071621b7d8> (a java.lang.Object)
    - locked <0x000000071621b7c8> (a java.lang.Object)

"Deadlock-2-B-then-A"
   java.lang.Thread.State: BLOCKED (on object monitor)
    at com.example.demo.liveness.DeadlockDemo.acquire(DeadlockDemo.java:27)
    - waiting to lock <0x000000071621b7c8> (a java.lang.Object)
    - locked <0x000000071621b7d8> (a java.lang.Object)
```

В конце дампа JVM явно сообщает:

```text
Found one Java-level deadlock:
=============================
"Deadlock-1-A-then-B":
  waiting to lock monitor 0x000077bc1c00dea0 (object 0x000000071621b7d8, a java.lang.Object),
  which is held by "Deadlock-2-B-then-A"

"Deadlock-2-B-then-A":
  waiting to lock monitor 0x000077bc10009980 (object 0x000000071621b7c8, a java.lang.Object),
  which is held by "Deadlock-1-A-then-B"
...
Found 1 deadlock.
```

| Поток | Удерживает | Ожидает | Состояние |
| --- | --- | --- | --- |
| `Deadlock-1-A-then-B` | A: `0x000000071621b7c8` | B: `0x000000071621b7d8` | `BLOCKED` |
| `Deadlock-2-B-then-A` | B: `0x000000071621b7d8` | A: `0x000000071621b7c8` | `BLOCKED` |

`locked` означает владение монитором, а `waiting to lock` — попытку войти в монитор, который принадлежит другому потоку. Совпадающие идентификаторы показывают замкнутый цикл ожидания. Адреса объектов зависят от запуска.

Основной поток находится в `WAITING` на `Thread.join()`: он ожидает завершения рабочих потоков, но не является участником цикла владения A/B. Служебные потоки JVM также присутствуют в дампе; их наличие в `WAITING` или `RUNNABLE` само по себе не говорит о deadlock. Для `ReentrantLock` ожидание обычно отображается как `WAITING` через park, поэтому нельзя искать все виды блокировок только по слову `BLOCKED`.

Альтернатива на Unix: `kill -3 <pid>` запрашивает у HotSpot дамп в вывод процесса. В данном задании использован именно `jstack`, приложен его полный результат.

## 4. Предотвращение Deadlock

Метод `orderedResources()` во всех потоках захватывает ресурсы в одном порядке: **A → B**, освобождает в обратном порядке в `finally`. Используется `ReentrantLock.lockInterruptibly()`, чтобы отмена проверочной задачи могла прервать ожидание.

Теперь поток, удерживающий B, уже владеет A; второй поток не может одновременно владеть A и ждать B. Циклическое ожидание исключено. Правило порядка должно соблюдаться во всех местах доступа к этим ресурсам, включая вызываемые методы.

Фактический результат:

```text
Deadlock prevention (A -> B): [10000, 10000]
```

Оба потока завершили по 10 000 операций. В исправленном алгоритме нет барьера внутри захваченного первого ресурса: такой барьер при общем порядке сам заблокировал бы прогресс второго участника.

## 5. Моделирование Livelock

В `livelock(rounds, false)` оба потока захватывают разные первые ресурсы и пытаются получить второй через неблокирующий `tryLock()`. Не получив его, освобождают первый ресурс и повторяют попытку. Это «вежливое» отступление не помогает, если участники постоянно действуют синхронно.

Два барьера на раунд воспроизводят неблагоприятное расписание:

1. Оба потока захватывают свои первые ресурсы.
2. Оба пробуют получить второй и получают отказ.
3. Только после обеих попыток освобождают первые ресурсы.
4. Повторяют те же действия.

Ни один поток не застрял навсегда на втором lock: число попыток растёт, но задачи не завершаются. Для безопасного наблюдения цикл ограничен 1000 раундами на поток. При удалении этого предела повторение такого расписания не даёт прогресса. Барьеры — средство контролируемого моделирования столкновений; короткие ожидания на них не означают, что потоки непрерывно занимают CPU.

Фактический результат:

```text
Livelock (bounded observation): LivelockResult[attempts=2000, completed=0]
```

Это демонстрация livelock на конечном окне наблюдения, а не оставленный работать бесконечный цикл.

### Исправление Livelock

В `livelock(rounds, true)` после конечного бюджета повторов потоки **меняют алгоритм**: переходят к общему порядку A → B и завершают по одной задаче. Просто остановить повторы недостаточно для успешного выполнения работы, поэтому реализован именно переход к стратегии с прогрессом.

```text
Livelock prevention (retry budget + A -> B): LivelockResult[attempts=20, completed=2]
```

Дополнительные возможные стратегии: общий deadline с явным возвратом ошибки, случайный backoff для рассинхронизации попыток, централизованная очередь запросов. Сам по себе одинаковый таймаут у обоих участников может сохранить синхронные столкновения. Случайный backoff уменьшает их вероятность, но в этой работе применён более предсказуемый выход через конечный бюджет и упорядоченный захват.

## 6. Моделирование Starvation

Метод `starvation()` создаёт владельца ресурса и ожидающего участника. Владелец захватывает `ReentrantLock(false)` и выполняет 10 000 своих операций, **не передавая ресурс между ними**. Второй поток уже стоит в очереди на тот же lock, что проверяется через `hasQueuedThread()`.

После работы владелец удерживает ресурс до внешнего разрешения проверочного потока. В этот момент фиксируется результат: владелец продвигается, ожидающий участник не выполнил ни одной операции. Затем контрольная логика разрешает освободить lock, и ожидающий участник завершает свою операцию.

```text
Starvation (controlled observation): StarvationResult[monopolistOperations=10000,
    victimWhileMonopolized=0, victimQueued=true, victimAfterRelease=1]
```

Это воспроизводимая модель голодания из-за монополизации ресурса на контролируемом интервале. Конечный тест не доказывает бесконечное ожидание; если владелец продолжает обслуживание только своей работы и не освобождает lock, ожидающий участник не сможет продвигаться. Здесь не заявляется, что `ReentrantLock(false)` всегда вызывает starvation: в примере причина прежде всего в длительном удержании ресурса, и справедливый lock без сокращения критической секции также не поможет.

От Deadlock ситуация отличается отсутствием замкнутого цикла: владелец не ждёт ресурса ожидающего потока. От Livelock — тем, что часть системы выполняет полезную работу, а конкретный участник лишён доступа.

### Исправление Starvation

В `fairAccess()` применяются два изменения:

- `ReentrantLock(true)` предоставляет справедливую очередь доступа для ожидающих участников.
- Ресурс освобождается после каждой короткой операции; внутри критической секции нет ожидания внешнего разрешения или длительного обслуживания собственной очереди.

Все потоки имеют обычные приоритеты. Используется `lockInterruptibly()`, а не неблокирующий `tryLock()`, который может обходить порядок справедливого lock.

Фактический результат четырёх потоков:

```text
Starvation prevention (fair lock, short sections): [1000, 1000, 1000, 1000]
```

Каждый выполнил по 1000 операций. Равные итоговые значения следуют из одинакового объёма задач; результат не означает строгого чередования потоков по времени. Справедливость lock относится к очереди доступа и не гарантирует справедливого планирования ОС или конкретного времени ожидания. Справедливая очередь может также снижать пропускную способность.

`Thread.yield()` — лишь подсказка планировщику, которую тот может проигнорировать. Понижение приоритета или `yield()` не обеспечивают освобождение уже удерживаемого lock и не дают надёжной гарантии против starvation. Поэтому основное исправление реализовано через короткие критические секции и справедливую очередь, а не через случайное влияние на расписание.

## 7. Корректные и некорректные ситуации

| Ситуация | Оценка |
| --- | --- |
| Два потока захватывают A/B в противоположном порядке | Возможен Deadlock; в примере барьер делает его воспроизводимым |
| Во всём приложении соблюдается порядок A → B | Исключается цикл ожидания этих двух ресурсов |
| `interrupt()` потока, ожидающего входа в `synchronized` | Не выводит его из ожидания монитора и не устраняет созданный deadlock |
| При неудаче `tryLock()` поток не освобождает уже захваченный ресурс | Может заблокировать остальных; освобождение требуется в `finally` |
| Оба участника бесконечно отступают и повторяют синхронно | Livelock: активность есть, полезного прогресса нет |
| Повторы ограничены, затем выполняется стратегия с общим порядком | Обе задачи завершаются в исправленном примере |
| Один владелец бесконечно обслуживает только себя под lock | Другие участники лишены доступа независимо от справедливости очереди |
| Короткие секции и справедливый lock | Уменьшают риск голодания при условии, что потоки получают процессорное время |
| Добавить `yield()` и считать проблему решённой | Некорректная гарантия: планировщик может проигнорировать подсказку |

Из `multithreading/demo` с JDK 17 или новее:

```sh

```

Сам `DeadlockDemo` намеренно не завершается. Для самостоятельной ручной диагностики его следует запускать в отдельной JVM, взять напечатанный PID и выполнить `jstack -l <pid>` из другого терминала. После дампа зависший процесс необходимо завершить; готовый скрипт делает это автоматически через trap.

Автоматические проверки охватывают: подтверждение настоящего deadlock в дочерней JVM и её принудительное завершение; выполнение обоих потоков при общем порядке ресурсов; нулевой прогресс при повторяющихся столкновениях; прогресс после смены алгоритма; отсутствие доступа у жертвы во время монополизации; завершение всех участников со справедливым lock; валидацию параметров.

Новые тесты имеют таймауты. Намеренный deadlock никогда не создаётся в тестовой JVM. Остальные задачи используют прерываемые ожидания, таймауты барьеров и завершение executor в `finally`.

Результаты проверки: компиляция `javac -Xlint:all` без предупреждений; **7 новых тестов — без ошибок и падений**; **полный набор из 40 тестов — без ошибок и падений**. Как и в предыдущем задании, полный запуск в sandbox выполнен с явным подключением уже загруженного Mockito к тестовой JVM через `-DargLine=-javaagent:/tmp/study-maven/repository/org/mockito/mockito-core/5.17.0/mockito-core-5.17.0.jar`. Новые проверки отдельно прошли без этого агента. Конфигурация существующего проекта не менялась.

## 9. Итоговые выводы

Deadlock — замкнутое ожидание ресурсов. В примере он подтверждён реальным дампом `jstack`: два потока `BLOCKED`, каждый удерживает монитор, нужный соседу. Общий порядок захвата устраняет цикл.

Livelock — повторение действий без выполнения задачи. Конечный бюджет повторов с переходом к упорядоченному захвату восстановил прогресс обоих участников.

Starvation — отсутствие прогресса у отдельных участников при продвижении других. Короткие критические секции и справедливая очередь дают ожидающим участникам доступ; одни приоритеты или `yield()` такой гарантии не предоставляют.

Для диагностики важно одновременно смотреть на владение ресурсами, состояния потоков и изменение счётчиков полезной работы. Один снимок со словом `WAITING`, высокая активность CPU или большое число попыток сами по себе не доказывают ни причину зависания, ни корректность алгоритма.
