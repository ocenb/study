# Краткий отчёт: многопоточная система событий и уведомлений

## 1. Реализация

В `src/main/java/com/example/demo/events/` добавлена система обработки событий по темам:

- `NotificationEvent` — неизменяемое событие: ID, тема, содержимое и время создания;
- `NotificationService` — публикация, подписка/отписка, доставка, статусы и журнал ошибок;
- `NotificationsApplication` — демонстрация с четырьмя производителями и четырьмя обработчиками.

Применены шаблоны **Producer–Consumer** и **Publish–Subscribe**: производители помещают события в общую очередь, обработчики извлекают их и вызывают подписчиков соответствующей темы.

## 2. Потокобезопасные коллекции

| Средство | Назначение |
| --- | --- |
| `ArrayBlockingQueue<NotificationEvent>` | Ограниченная очередь событий, ёмкость в демонстрации — 2048 |
| `ConcurrentHashMap` | Реестр подписчиков по темам и статусы событий по ID |
| `CopyOnWriteArrayList<Subscriber>` | Безопасный обход подписчиков при одновременных подписке и отписке |
| `ConcurrentLinkedQueue<DeliveryFailure>` | Журнал ошибок доставки без общего блокирующего списка |
| `LongAdder` | Конкурентные счётчики публикаций, доставок, повторов и ошибок |

В демонстрации журналы аудита и отправленных уведомлений также используют `ConcurrentLinkedQueue`.

Событие и записи статуса неизменяемы. Короткая секция `synchronized` согласует публикацию с закрытием сервиса и связывает несколько действий: проверку ID, резервирование статуса и помещение в очередь. Потокобезопасность отдельных коллекций сама по себе не делает такую последовательность атомарной. Пользовательские обработчики выполняются вне этой секции.

## 3. Доставка и обработка ошибок

Для каждой темы можно зарегистрировать несколько подписчиков. Повторная регистрация того же подписчика игнорируется. При доставке используется снимок итератора `CopyOnWriteArrayList`: отписка влияет на следующие обходы, но не отменяет уже начатый.

`publish()` возвращает один из результатов:

- `ACCEPTED` — событие принято;
- `DUPLICATE` — такой ID уже принят ранее;
- `QUEUE_FULL` — очередь заполнена; событие не принято, его ID можно отправить повторно.

Статус проходит этапы `QUEUED → PROCESSING → COMPLETED` либо `COMPLETED_WITH_ERRORS`. Ошибка подписчика записывается с ID события, темой и временем; другие подписчики и следующие события продолжают обрабатываться. Событие без подписчиков завершается с нулём доставок.

Собственный `ExecutorService` запускает четыре обработчика с именами `notification-dispatch-N`. При `close()` сервис прекращает приём и обрабатывает накопленную очередь, затем завершает пул. При превышении срока ожидания запрашивает прерывание и сообщает об ошибке завершения. Вызов `close()` из подписчика отклоняется, чтобы обработчик не ожидал завершения самого себя.

## 5. Проверка и запуск

Добавлены семь тестов: конкурентные производители без потерь и повторных доставок; изоляция ошибок; переполнение очереди и повторная отправка; отписка во время обхода снимка; завершение принятых событий при закрытии; отсутствие подписчиков и защита от закрытия из callback; проверка параметров.

Из `multithreading/demo` с JDK 17 или новее:

```sh
mkdir -p target/events-demo
javac -encoding UTF-8 -d target/events-demo src/main/java/com/example/demo/events/*.java
java -cp target/events-demo com.example.demo.events.NotificationsApplication

sh ./mvnw -Dtest=com.example.demo.events.NotificationServiceTest test
sh ./mvnw test
```

Проверки завершились успешно: **7 новых тестов и полный набор из 73 тестов — без ошибок и падений**. Компиляция с `javac -Xlint:all` прошла без предупреждений. Для полного набора использовались локальные сокеты вне sandbox и явный Mockito javaagent для существующих тестов; новые проверки отдельно прошли без сети и агента.

## Вывод

Потокобезопасные коллекции позволили разделить приём событий, параллельную доставку, управление подписками и наблюдение за результатами. Ограниченная очередь обеспечивает явный отказ при перегрузке, а обработка исключений изолирует сбой отдельного подписчика.

Это система в памяти: статусы и ошибки сохраняются в течение жизни экземпляра, автоматических повторных попыток и постоянного хранилища нет. Дедупликация действует по глобальному ID события в рамках экземпляра; после перезапуска она не сохраняется. При нескольких обработчиках порядок завершения событий не гарантируется. Счётчики во время работы являются наблюдаемым снимком; итоговые значения проверяются после закрытия.
