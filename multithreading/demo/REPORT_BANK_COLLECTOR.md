# Отчёт о выполнении практического задания: Реализация банковского аккаунта и DataCollector

## 1. Введение и постановка задачи
Цель работы — разработка многопоточной системы сбора данных и управления банковскими счетами, обеспечивающей строгую корректность данных в условиях конкурентного доступа:
* Исключение состояния гонки данных (**Race Condition**).
* Гарантированное предотвращение взаимных блокировок (**Deadlock**).
* Управление жизненным циклом и ожиданием готовности данных с помощью связки **`wait()`**, **`notify()`** и **`notifyAll()`**.
* Сравнение производительности и целостности синхронизированных и несинхронизированных операций.

## 3. Этапы выполнения задания

### Этап 1. Защита от гонки данных (DataCollector и BankAccount)
* Все операции изменения состояния (`balance += amount`, `processedCount++`, добавление в коллекции `processedKeys` и `collectedItems`) обёрнуты в `synchronized`.
* Это гарантирует атомарность операции **«чтение-модификация-запись»** (Read-Modify-Write), предотвращая потерю инкрементов и повреждение внутренних структур коллекций (например, повреждение бакетов в `HashSet`).

### Этап 2. Реализация ожидания и уведомления (`wait()` и `notifyAll()`)
* **Сценарий со счётом (`withdrawWithWait`)**:
  Если на балансе недостаточно средств, поток входит в цикл ожидания:
  ```java
  while (balance < amount) {
      wait(remaining);
  }
  ```
  Использование цикла `while` критически важно для защиты от **ложных пробуждений** (Spurious Wakeups).
  При вызове метода `deposit()` поток-пополнитель вызывает `notifyAll()`, пробуждая ожидающие потоки для повторной проверки условия.
* **Сценарий с коллектором (`DataCollector.waitUntilProcessedCount`)**:
  Потребитель ожидает, пока продюсеры не соберут целевое количество элементов. Каждый успешный `collectItem()` вызывает `notifyAll()`.

### Этап 3. Предотвращение взаимных блокировок (Deadlock)

#### Некорректная ситуация (Deadlock):
Поток 1 переводит средства со счёта $A$ на счёт $B$, а Поток 2 — со счёта $B$ на счёт $A$:
1. Поток 1 блокирует `synchronized(A)` и готовится захватить `B`.
2. Поток 2 блокирует `synchronized(B)` и готовится захватить `A`.
3. **Взаимная блокировка (Deadlock)**: оба потока ждут освобождения мониторов друг друга бесконечно (циклическое ожидание, условие Коффмана №4).

#### Корректная ситуация (Deadlock Prevention):
В методе `transferSafe` реализовано упорядочивание захвата ресурсов по идентификатору счёта:
```java
BankAccount firstLock = from.getId() < to.getId() ? from : to;
BankAccount secondLock = from.getId() < to.getId() ? to : from;

synchronized (firstLock) {
    synchronized (secondLock) {
        if (from.withdraw(amount)) {
            to.deposit(amount);
            return true;
        }
        return false;
    }
}
```
**Результат**: Независимо от направления перевода ($A \rightarrow B$ или $B \rightarrow A$), оба потока всегда стремятся сначала захватить счёт с меньшим ID, а затем — с большим. Возникновение замкнутого цикла ожидания математически невозможно!

## 5. Итоговые выводы

1. **Необходимость синхронизации**:
   * Любые разделяемые изменяемые данные (Shared Mutable State) обязаны быть защищены примитивами синхронизации (`synchronized`, `ReentrantLock`, `Atomic*`). Отсутствие синхронизации приводит к недетерминированным ошибкам в продакшене, которые крайне сложно воспроизвести и отладить.
2. **Безопасность ожидания**:
   * Методы `wait()` и `notifyAll()` должны вызываться исключительно внутри синхронизированного контекста на объекте монитора. Проверка условия продолжения работы обязательно должна выполняться внутри цикла `while`, а не `if`.
3. **Иерархия блокировок**:
   * При одновременном захвате нескольких мониторов единственный надежный способ избежать взаимных блокировок без таймаутов — введение строгого глобального порядка блокировок (например, сортировка по первичному ключу ID).
