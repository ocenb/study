## 2. Future и отмена долгой задачи

Создан `ExecutorService` с одним рабочим потоком. Через `submit()` отправлена задача, имитирующая **8 секунд** обработки. Полученный `Future` отменяется через **2,5 секунды после подтверждённого старта** вызовом `cancel(true)`.

Задача ожидает в прерываемом `sleep()`, обрабатывает `InterruptedException`, восстанавливает флаг прерывания и завершает работу. После отмены проверяются отдельно состояние Future, исключение при `get()` и фактическое завершение кода задачи через `CountDownLatch`.

Фактический результат:

```text
cancelAccepted=true
cancelled=true
done=true
interrupted=true
workerStopped=true
getThrewCancellation=true
elapsedMillis=2508.204664
```

Отмена принята, задача прервана примерно через **2,51 секунды**, а `get()` выбросил `CancellationException`. `isDone()` равен `true` и для отменённой задачи: это не признак успешного результата. Сам `cancel(true)` лишь запрашивает прерывание; игнорирующая interrupt задача может продолжить работу. При `cancel(false)` прерывание работающего потока не запрашивается. Уже завершённую задачу отменить нельзя — этот случай также проверяется тестом.

## 3. Пять задач через invokeAll

Создан список из **пяти Callable** и пул из пяти потоков. Каждая задача выбирает случайную длительность **1000–3000 мс**, ожидает её и возвращает идентификатор, плановую и фактическую длительности, а также число `id * 10`.

Все задачи передаются одним вызовом `invokeAll(tasks)`. Метод ожидает завершения всей партии, после чего результаты читаются через `Future.get()`. Список Future соответствует порядку входных задач, а не порядку завершения. Ошибка Callable доступна через `ExecutionException` при чтении её Future; прерывание вызывающего потока отменяет незавершённые задачи invokeAll.

Фактический запуск:

| Задача | Плановая длительность, мс | Фактическая, мс | Результат |
| ---: | ---: | ---: | ---: |
| 1 | 1248 | 1248,097 | 10 |
| 2 | 1058 | 1058,184 | 20 |
| 3 | 1953 | 1953,111 | 30 |
| 4 | 1458 | 1458,101 | 40 |
| 5 | 1689 | 1689,152 | 50 |

Вся партия заняла **1960,157 мс**, то есть примерно время самой долгой задачи, а не сумму задержек **7406 мс**. При повторном запуске случайные длительности изменятся; планировщик может увеличить фактическое время.

## 4. ScheduledExecutorService

Создан отдельный `ScheduledExecutorService`. Через `scheduleAtFixedRate()` с начальной задержкой 0 и периодом **1 секунда** запускается фоновая проверка статуса:

```text
Проверка #1: система работает
Проверка #2: система работает
Проверка #3: система работает
Проверок выполнено: 3
```

Демонстрация ограничена тремя проверками, после чего отменяется `ScheduledFuture` и закрывается scheduler. Период задаёт плановые моменты запуска, а не гарантию точного времени выполнения. Необработанное исключение в периодической задаче может остановить её дальнейшие запуски; поэтому в более сложном агрегаторе ошибки источника и обработки перехватываются.

## 5. PeriodicDataAggregator

Сервис принимает интервал `Duration`, размер рабочего пула, `DataSource`, обработчик успешных результатов и обработчик ошибок. В демонстрации **N = 1 секунда**, три рабочих потока и три идентификатора: **USD, EUR, CNY**.

Каждый цикл:

1. Заново получает актуальный список идентификаторов через `identifiers()`.
2. Отправляет отдельные запросы `fetch(id)` в рабочий `ExecutorService`, не ожидая каждый последовательно.
3. Передаёт успешные данные в обработчик: он логирует их и сохраняет последнее значение в `ConcurrentHashMap`.
4. Отдельно учитывает ошибки и завершает цикл после всех запросов.

Первый запрос EUR намеренно выбрасывает `IOException`; остальные данные первого цикла сохраняются. Следующие циклы продолжаются, и EUR успешно обновляется. Ошибки получения списка и сохранения также перехватываются, чтобы не остановить расписание. Внутри цикла повторных попыток нет: очередной опрос выполняется следующим циклом.

Если предыдущий цикл ещё работает, очередной такт **пропускается** и увеличивает `skippedTicks`. Это предотвращает наложение циклов и бесконечное накопление одинаковых запросов при медленном источнике. Scheduler и рабочий пул разделены. Обработчики результатов вызываются параллельно, поэтому хранилище должно быть потокобезопасным.

Фактическая сводка после трёх циклов:

```text
startedCycles=3, completedCycles=3, skippedTicks=0
successes=8, failures=1
Сохранённые сущности: [CNY, EUR, USD]
```

Восемь успешных обработок обновили три записи: хранилище содержит последнее значение каждой сущности. После `close()` получены `closed=true`, `collecting=false`, `terminated=true`. Закрытие отменяет расписание и текущие Future с прерыванием, завершает оба пула и ожидает их остановки. Источник должен учитывать interrupt; принудительное безопасное завершение произвольного кода через Future не обеспечивается.

## 6. Проверки и выводы

Добавлены восемь тестов: отмена выполняющейся задачи, невозможность отменить завершённую, пять результатов invokeAll, периодический мониторинг, параллельный сбор и восстановление после ошибки сущности, пропуск тактов и прерывание при закрытии, восстановление после ошибок списка/хранилища, пустой список и жизненный цикл сервиса. Параллельность запросов подтверждается барьером: все три запроса должны войти в источник до его первого ответа.

Проверки завершились успешно: **8 новых тестов и полный набор из 55 тестов — без ошибок и падений**. Компиляция `javac -Xlint:all` не выдала предупреждений. Полный набор запускался с доступом к локальным сокетам для ранее добавленных HTTP-тестов и с явным Mockito javaagent, как в предыдущих заданиях; новые тесты отдельно прошли в sandbox без агента.

`Future` позволяет получать результат и запрашивать отмену, но физическая остановка требует сотрудничества задачи. `invokeAll()` удобен для ожидания независимой партии. `ScheduledExecutorService` обеспечивает периодические запуски, а отдельный рабочий пул, обработка исключений и защита от наложения циклов позволяют агрегатору продолжать работу при отдельных сбоях.
