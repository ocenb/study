# Отчёт: параллельный сбор данных через CompletableFuture

## 1. Состав решения и внешние источники

Решение находится в `src/main/java/com/example/demo/completable/`:

| Класс | Назначение |
| --- | --- |
| `OrderDataService` | Асинхронная и последовательная версии сбора, преобразование, сохранение |
| `FileOrderDataSource` | Чтение трёх независимых внешних CSV-файлов |
| `CompletableOrdersApplication` | Демонстрация частичного результата и сравнение времени |

Данные читаются из UTF-8 файлов в `order-data/`, а не генерируются внутри конвейера:

- `users.csv`: `requestId;userName`;
- `products.csv`: `requestId;productName;priceUsd`;
- `rates.csv`: `requestId;rubPerUsd`.

Формат учебный: разделитель `;`, без кавычек и вложенных разделителей; строки с `#` — комментарии. Цены и курс вымышлены. Входной список демонстрации — `P1, P2, P3, P4, P5`. Для отсутствующего ID источник выбрасывает `IOException`.

## 2. Получение пользователя, товара и курса

Реализован метод с требуемой сигнатурой:

```java
public List<FinalResult> fetchAllDataAsync(List<String> ids)
```

Для каждого ID три независимых обращения выполняются через `CompletableFuture.supplyAsync(..., executor)`: получение пользователя, товара и курса. Запускаются конвейеры всех ID, затем координатор ожидает их завершения через `allOf()`. Метод возвращает готовый список, поэтому сам вызывающий поток ожидает сбор; параллельно выполняются внутренние операции. Порядок успешных результатов соответствует порядку входных ID, повторы сохраняются.

Используется собственный `ExecutorService` из **шести именованных демон-потоков** `order-data-1` и далее. Все вызовы `supplyAsync` и `thenApplyAsync` получают этот executor явно; `ForkJoinPool.commonPool` не используется. Шесть потоков ограничивают одновременное выполнение операций и позволяют перекрывать ожидание нескольких источников.

Каждое чтение выполняется заново из соответствующего файла. Для моделирования задержек источника добавлены ожидания: пользователь — **80 мс**, товар — **120 мс**, курс — **100 мс**.

## 3. Преобразование, объединение и вычисление цены

Конвейер использует необходимые операции:

1. **`thenApply`** нормализует название товара: удаляет крайние и повторяющиеся пробелы. Это короткое неблокирующее преобразование.
2. **`thenCombine`** объединяет независимые результаты товара и курса в `PricedProduct`.
3. Второй **`thenCombine`** добавляет пользователя к данным покупки.
4. **`thenApplyAsync(..., executor)`** выполняет обогащение с имитацией тяжёлой/блокирующей обработки **40 мс** и вычисляет рублёвую цену.
5. Ещё один **`thenApplyAsync(..., executor)`** сохраняет заказ; имитация задержки сохранения — **30 мс**.
6. **`thenAccept`** логирует факт успешного сохранения. Завершение этой стадии также учитывается при сборе результата.

Короткие стадии без суффикса Async могут выполняться потоком, завершающим предыдущую стадию, либо вызывающим потоком, если результат уже готов. Тяжёлое преобразование и сохранение явно переданы собственному пулу. Внутри рабочих задач нет ожиданий `join()` других задач этого пула.

Цена рассчитывается через `BigDecimal`, округление до двух знаков — `HALF_UP`:

```text
10.25 USD × 92.45 RUB/USD = 947.6125 RUB → 947.61 RUB
```

Итоговый `FinalResult` содержит ID запроса, имя пользователя, нормализованное название товара, исходную и рублёвую цены.

## 4. Сохранение, трассировка и обработка ошибок

Сохранение выполняется через интерфейс `OrderStore`. В демонстрации это потокобезопасный `ConcurrentHashMap`: для каждого ID хранится последний успешно сохранённый заказ. Метод возвращает только заказы с успешно завершённым сохранением.

Логи включают ID запроса, имя потока и этап. Примеры из фактического запуска:

```text
request=P1 thread=order-data-2 stage=thenApply:normalize
request=P3 thread=order-data-4 stage=ERROR:IOException:Имитация недоступного курса для P3
```

Имена конкретных рабочих потоков и порядок строк могут меняться между запусками.

На каждом итоговом конвейере применяется **`handle`**. Ошибка чтения, преобразования или сохранения логируется и превращается в пустой `Optional`; при сборе списка этот ID пропускается. Успешные задачи не отменяются из-за сбоя соседа. Если не успешна ни одна задача, возвращается пустой список.

Для **P3** ошибка источника курса задана намеренно, несмотря на наличие записи в CSV. Для остальных ID чтение, расчёт и сохранение продолжаются. Фактический промежуточный результат:

```text
Входных ID=5; результатов=4; сохранённых заказов=4
Успешные ID: P1, P2, P4, P5
Рублёвая цена каждого успешного заказа: 947.61
Executor terminated=true
```

Сервис используется через `try-with-resources`. `close()` вызывает `shutdown()`, ожидает завершения и при превышении срока использует `shutdownNow()`. Демон-статус не заменяет явное закрытие: завершение JVM само по себе не гарантирует окончания фонового сохранения.

## 5. Сравнение последовательной и асинхронной версий

`fetchAllDataSync()` использует те же файлы, задержки, нормализацию, округление, правило частичных ошибок и сохранение, но выполняет операции последовательно. На каждом измерении создаются отдельное хранилище и сервис. Вывод трассировки отключён в обоих вариантах.

Проведён один прогрев каждого варианта и три измерения; порядок вариантов чередовался. После каждой пары проверялось полное равенство итоговых объектов. Время измерялось через `System.nanoTime()` от вызова метода до получения списка. Создание и закрытие сервиса находятся вне замера; создание рабочих потоков по мере необходимости входит во время асинхронного метода.

Среда: OpenJDK **17.0.20.1**, Linux, собственный пул из шести потоков.

| Замер | Последовательно, мс | Асинхронно, мс | Результат |
| ---: | ---: | ---: | --- |
| 1 | 1790,548 | 373,669 | 4 одинаковых объекта |
| 2 | 1787,795 | 372,774 | 4 одинаковых объекта |
| 3 | 1787,098 | 372,707 | 4 одинаковых объекта |
| Медиана | **1787,795** | **372,774** | **Ускорение 4,80×** |

Полный вывод, включая трассировку и итоговые объекты: [COMPLETABLE_RESULTS.txt](COMPLETABLE_RESULTS.txt).

Ускорение объясняется перекрытием имитируемых ожиданий независимых операций. Это учебный замер с задержками `sleep()`, а не универсальная оценка быстродействия CompletableFuture. Для другой нагрузки результат зависит от числа потоков, стоимости преобразований, ограничений источников и оборудования.

## 6. Запуск и проверки

Из каталога `multithreading/demo` с JDK 17 или новее; каталог `order-data/` должен находиться в текущей рабочей директории:

```sh
mkdir -p target/completable-demo
javac -encoding UTF-8 -d target/completable-demo src/main/java/com/example/demo/completable/*.java
java -cp target/completable-demo com.example.demo.completable.CompletableOrdersApplication

sh ./mvnw -Dtest=com.example.demo.completable.OrderDataServiceTest test
sh ./mvnw test
```

Шесть новых тестов проверяют чтение внешних файлов и отсутствующий ID, одновременное выполнение трёх источников, именованные демон-потоки и поток тяжёлого преобразования, расчёт цены и нормализацию, частичный результат при сбое курса, ошибку сохранения, равенство версий и повторяющиеся ID, пустой/полностью неуспешный список и завершение executor. Параллельность источников проверяется общей точкой ожидания: все три должны начать работу до первого ответа.

Проверки завершились успешно: **6 новых тестов и полный набор из 61 теста — без ошибок и падений**. Компиляция с `javac -Xlint:all` прошла без предупреждений. Полный набор проверялся с локальными сокетами для существующих HTTP-тестов и явным Mockito javaagent, как в предыдущих заданиях; новые проверки отдельно прошли в sandbox без агента.

## Выводы

`thenApply` выполняет простое преобразование, `thenCombine` связывает независимые результаты, а `thenAccept` обрабатывает успешное завершение без возвращаемого значения. Для тяжёлой обработки нужен `thenApplyAsync` с явно переданным executor. Обработка ошибок через `handle` сохранила четыре успешных заказа при сбое пятого; явное закрытие пула завершило работу приложения корректно. Асинхронная версия вернула те же объекты и в данном эксперименте имела меньшую длительность.
